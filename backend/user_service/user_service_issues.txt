5. Refresh tokens: no rotation, no reuse-detection, no hashing

Problems:

Refresh tokens are not rotated on /refresh. The same refresh can be used repeatedly until expiry — a stolen refresh token never burns.
No reuse detection. If an attacker uses your refresh, you have no way to know and invalidate the family.
Stored as raw token → anyone with Redis read access gets valid tokens. Store a hash (sha256) as the Redis key, not the raw token.
Redis key is not bound to a device/session.

6. Email/password reset tokens are replayable

Also, these tokens are full JWTs signed with the app secret and are sent via events to another service that emails them. You are committing the secret-signed token to the message bus; if RabbitMQ ACLs/mTLS are weak, that's account takeover material. 3. Password-reset / verification tokens are long-lived, replayable JWTs stored in plaintext in your DB and broadcast on the bus
user_service.py:86–99 (register), 321–341 (reset request), outbox_event_service.py:18–24

copy
reset_token, _ = self.token_manager.create_access_token(..., purpose="password_reset")
await self.outbox_event_service.add_outbox_event(
    event_type=UserEvents.USER_PASSWORD_RESET_REQUEST,
    payload=PasswordResetRequestedEvent(user_email=..., reset_token=reset_token, ...))
Four compounding problems:

Not single-use. reset_password_with_token only checks the JWT signature + purpose. The same token resets the password again and again until exp. Attacker who sees one reset link owns the account for the whole TTL.
Persisted forever in plaintext. payload_dict lands in the outbox_events table. Nothing purges processed rows. A read-only DB dump / analytics replica / backup = a pile of valid credential-reset tokens.
Fanned out to every consumer bound to user.events.exchange. Notification service needs the token; analytics and audit services don't, and they now have it.
Password reset doesn't revoke sessions. After reset_password_with_token, every previously issued refresh token is still live in Redis. The attacker whose password you just "reset away from" stays logged in indefinitely.
Fix:

Store a random 32-byte secret (secrets.token_urlsafe(32)) in Redis/a password_resets table keyed by sha256(token), with used_at, expires_at, single-use GETDEL/UPDATE ... WHERE used_at IS NULL. JWTs are the wrong primitive here — you cannot revoke them.
Put only {user_id, reset_id} in the event payload; let the notification service fetch/compose, or at minimum encrypt the token column.
Add outbox_events retention (DELETE WHERE processed AND processed_at < now() - interval '7 days') as a scheduled job.
On password reset and on email change: bump a per-user token_version / delete refresh:* for that user → forces global logout.
4. Refresh tokens: no rotation, no reuse detection, no revocation, stored raw
user_service.py:64, 192–201, 404–426

copy

Raw token as the Redis key → anyone with KEYS refresh:* (Redis compromise, MONITOR, a rogue service sharing the instance, a Redis slowlog) gets directly usable bearer credentials. Store sha256(token).
No rotation. /refresh mints a new access token and leaves the same refresh token valid. A stolen refresh token is a permanent account takeover for REFRESH_TOKEN_TIME_DELTA_DAYS. You cannot even detect the theft.
Stale claims. refresh_access_token re-signs role and email straight out of the old token (line 415-419) without re-reading the DB. Demote an admin → they keep minting admin access tokens until the refresh expires. Deactivate / delete a user → same. Ban is meaningless.
No jti/denylist on access tokens. DELETE /users/{id} removes the row; their access token keeps working until exp. logout_user deletes the refresh key but the access token lives on.
No refresh:user:{id} index → "log out all devices" is impossible.
Fix (standard rotating-refresh family):

copy
async def refresh_access_token(self, refresh_token: str):
    data = self.token_manager.decode_token(refresh_token, required_purpose="refresh")
    key = self._refresh_key(sha256(refresh_token))
    user_id = await self.redis.getdel(key)            # atomic single-use
    if not user_id:
        await self._revoke_all_for_user(data.id)      # reuse => breach => nuke family
        raise HTTPException(401, "Refresh token reuse detected")
    user = await self.repository.get_by_id(data.id)
    if not user or not user.is_active:
        raise HTTPException(401, "Account disabled")
    new_refresh, _ = self.token_manager.create_refresh_token(email=user.email, user_id=user.id, role=user.role)
    await self._store_refresh(user.id, new_refresh)   # also SADD refresh:user:{id}
    return self.token_manager.create_access_token(email=user.email, user_id=user.id, role=user.role, purpose="access")
Keep access tokens ≤ 5–15 min, and add a token_version claim checked against the DB/cache so you get cheap global invalidation.

Endpoint	Limit
/login	5/min per IP, 10/hour per email, exponential lockout after 5 fails
/register	3/hour per IP
/forgot-password	3/hour per email, 10/hour per IP
/password-reset/{token}, /activate/{token}	10/hour per IP
/refresh	30/min per user

🟠 P1 — Correctness / data-integrity bugs
8. The outbox poller has a poison-message head-of-line block
outbox_poller_service.py:23–70

copy
event_type = event_data.get("event_type")   # read from the *payload*, not the column
match event_type:
    ...
    case _: self.logger.warning(f"Unhandled event type ...")   # never marked processed
Routing reads event.payload["event_type"], ignoring the authoritative OutboxEvent.event_type column you just wrote. If they ever diverge (schema change, new event), the row falls into case _, logs a warning, is never marked processed, and is re-fetched in the same first 50 rows on every single poll, forever. Same for any event that permanently fails to publish (malformed payload, consumer-rejected). One bad row stops the entire outbox.
There is no attempt counter, no backoff, no dead-letter. Add attempts, last_error, next_retry_at, and WHERE processed = false AND next_retry_at <= now() ORDER BY created_at LIMIT 50 FOR UPDATE SKIP LOCKED; move rows over max_attempts to a outbox_events_dead table + alert.
RabbitMQ I/O happens while holding FOR UPDATE row locks inside an open Postgres transaction (up to 50 network round-trips). That's a long-lived transaction pinning locks and bloating the DB. Fetch + mark in short transactions; publish between them.
SKIP LOCKED must be confirmed. get_many_by_field_with_lock lives in shared/ (not in this archive). Without SKIP LOCKED, your GUNICORN_WORKERS pollers serialize and block each other. Worse: every gunicorn worker and every pod replica starts its own poller (main.py:43). You're running N× pollers against the same table with zero leader election. Either run the poller as a separate single-replica deployment / leader-elected sidecar, or gate it on if os.getenv("RUN_OUTBOX_POLLER").
Events have no event_id in the payload → consumers cannot deduplicate. Your delivery is at-least-once (publish succeeds, mark_event_as_processed commit fails → republish). Put event_id, occurred_at, schema_version, and a correlation_id/trace_id in every payload, and have consumers keep an processed_events(event_id) unique table.
Confirm BaseEventPublisher uses publisher confirms (publisher_confirms=True, mandatory=True) and that the exchange/queues are durable + messages delivery_mode=2. Without confirms, publish() returns immediately and you mark-processed a message RabbitMQ never persisted → silent data loss.

13. Secrets-in-URL on /activate/{token} and /password-reset/{token}
routes/user_routes.py:41, 75. Path parameters land in: nginx/ALB access logs, your own --access-logfile - gunicorn logs, OTel span names/attributes, browser history, and Referer headers to any third-party script on the landing page. Credentials belong in the body (POST /password-reset with {"token": ..., "new_password": ...}) or, at minimum, scrub them in the logging middleware + OTel span processor.

14. Verifying an email auto-issues an access token
verify_email (user_service.py:270–292) returns a live access token. Clicking a link in an email (which may be prefetched by a mail scanner, a corporate proxy, or Safe Links) now yields session credentials in a URL the user didn't control. Verify, then redirect to login.

15. Hard DELETE of users in an event-driven system
user_service.py:294–312. Orders, carts, reviews, and ledgers in sibling services hold user_id. A hard delete produces dangling references in every downstream read-model, and you can't audit it. Use soft-delete (deleted_at, is_active=False) + an explicit anonymization flow for GDPR erasure (scrub PII in place, keep the row + id). 16. Every login writes a DB row
login_user → add_outbox_event(USER_LOGGED_IN) on the hot path. That's a synchronous INSERT + commit + a RabbitMQ publish per login, plus a row in the outbox table that grows monotonically. Login analytics do not need exactly-once transactional delivery. Either drop it from the outbox (emit via the logging/metrics pipeline) or accept the cost consciously and make sure outbox retention is in place.
